# Фронтенд на Cloudflare Pages, API на VPS

Целевая схема:

| Что | Адрес | Где работает |
| --- | --- | --- |
| Сайт | `https://bln.vladislavb.qzz.io/` | Cloudflare Pages, статическая сборка `web/dist` |
| API | `https://vps.vladislavb.qzz.io/api/` | существующий сервер VPS |
| WebSocket | `wss://vps.vladislavb.qzz.io/ws` | тот же VPS |

Подготовка файлов в репозитории сама по себе ничего не публикует. Первое реальное размещение произойдёт, когда владелец настроит Cloudflare и GitHub и изменения попадут в `main`. Код API, базу и DNS VPS переносить не нужно. Домен `vladinc.ru` и его сайт эта схема не использует и не меняет.

Это разные **origin**, поэтому API должен разрешать `https://bln.vladislavb.qzz.io` через CORS. Но при HTTPS они относятся к одному сайту `vladislavb.qzz.io`: существующие сессионные cookie `SameSite=Lax` должны работать без изменения кода API или прокси. После настройки это всё равно нужно проверить в браузере, включая WebSocket.

## 1. Создайте пустой проект Pages

Нужен доступ к аккаунту Cloudflare и DNS зоны `vladislavb.qzz.io`. Для GitHub Actions создаётся проект **Cloudflare Pages с Direct Upload**, а не Worker. У существующего проекта убедитесь, что он предназначен для этого сайта, а его production-ветка — `main`.

Один из способов создать пустой проект — на своём компьютере с Node.js **22** выполнить:

```bash
npx --yes wrangler@4.156.1 login
npx --yes wrangler@4.156.1 pages project create balesnolandia-frontend --production-branch=main
```

Вход подтверждается в открывшемся браузере Cloudflare. Вторая команда создаёт пустой проект, но не загружает сайт. Если имя занято или выбрано другое — запомните фактическое имя. На первом запуске GitHub Actions проект уже должен существовать.

Проект Direct Upload не переключается на Git-интеграцию Pages; для другого способа понадобится новый проект. В этой инструкции сборку и загрузку выполняет **GitHub Actions**, поэтому подключать Git в панели Pages не требуется. Подробнее: [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

## 2. Настройте GitHub Actions

В репозитории откройте **Settings → Environments**, создайте окружение `cloudflare-pages` и добавьте в нём:

| Тип | Имя | Что указать |
| --- | --- | --- |
| Environment variable | `CLOUDFLARE_PAGES_PROJECT` | точное имя созданного проекта Pages, например `balesnolandia-frontend` |
| Environment secret | `CLOUDFLARE_ACCOUNT_ID` | ID аккаунта Cloudflare, где находится проект |
| Environment secret | `CLOUDFLARE_API_TOKEN` | отдельный ограниченный токен для публикации Pages |

Токен создаётся в Cloudflare с правом **Account → Cloudflare Pages → Edit**, ограниченным нужным аккаунтом. Доступ к DNS для этого токена не нужен: домен подключается отдельно в панели. Официальная инструкция: [Cloudflare Pages + GitHub Actions](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/).

**Не присылайте токен в чат и не сохраняйте его в репозитории.** Вставьте значения секретов непосредственно в настройки GitHub. Если у окружения есть правила подтверждения или ограничения веток, разрешите публикацию из `main` и подтвердите запуск, когда GitHub попросит.

Для существующего workflow API в окружении `production` проверьте переменные `SITE_DOMAIN` и `API_DOMAIN`. Если они заданы, их значения имеют приоритет над значениями по умолчанию. Для новой схемы нужны соответственно `bln.vladislavb.qzz.io` и `vps.vladislavb.qzz.io` **без** `https://` и путей. Это влияет на настройки, записываемые при *следующей* публикации API, но само по себе API не перезапускает.

## 3. Запустите первую публикацию фронтенда

После проверки настроек владелец переносит эти изменения в `main` обычным для проекта способом. При изменении фронтенда, `shared` или workflow публикации в `main` автоматически запустится **Deploy frontend to Cloudflare Pages**. Он:

1. выполняет lint и тесты на отдельной тестовой MariaDB;
2. собирает сайт в `web/dist` с `BASE_PATH=/`, `VITE_API_URL=https://vps.vladislavb.qzz.io` и `VITE_WS_URL=wss://vps.vladislavb.qzz.io/ws`;
3. проверяет страницы, PWA-файлы и адреса в сборке;
4. загружает в Pages только проверенное содержимое `web/dist`.

Ветка `main` должна быть production-веткой проекта Pages. Ручной запуск workflow также допускает публикацию **только из `main`**. Если первый запуск завершился ошибкой из-за отсутствующих настроек, внесите их и в GitHub Actions нажмите **Re-run failed jobs** у этого запуска.

Кнопка **Run workflow** доступна, только когда файл workflow присутствует в default-ветке GitHub. На момент подготовки default-ветка этого репозитория — `claude/stoic-mccarthy-xllyfx`, а производственная ветка настроена как `main`. Это не мешает автоматическому запуску при push в `main`; для ручного запуска убедитесь, что workflow также находится в default-ветке и выберите `main`.

После первого успешного запуска появится адрес `*.pages.dev`. Это другой сайт с точки зрения cookies: вход через существующий API на нём может не работать. Для полноценной проверки используйте собственный домен из следующего шага.

## 4. Подключите `bln.vladislavb.qzz.io`

1. Откройте в Cloudflare **Workers & Pages → ваш проект → Custom domains → Set up a domain**.
2. Добавьте `bln.vladislavb.qzz.io`. Если Pages предлагает добавить DNS-запись автоматически, проверьте её перед подтверждением. При ручной настройке после добавления домена в Pages создайте в зоне `vladislavb.qzz.io` CNAME для `bln` на адрес проекта `*.pages.dev`, указанный Cloudflare.
3. Дождитесь активации домена и сертификата HTTPS. Добавить только CNAME без регистрации домена в самом Pages недостаточно.
4. Не изменяйте запись `vps`, NS зоны, чужие записи или домен `vladinc.ru`. Проверяйте только новый поддомен `bln`.

Если сертификат долго не выпускается, проверьте наличие конфликтующей DNS-записи для `bln` и ограничения CAA. Инструкция Cloudflare: [Custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/).

## 5. Разрешите новый сайт в настройках API

В существующей админке откройте **Система → Адреса и почта**:

1. Добавьте `https://bln.vladislavb.qzz.io` в поле **Дополнительные адреса фронтенда (CORS)**, не удаляя другие нужные адреса. Это origin без завершающего пути.
2. Когда новый сайт уже доступен, установите **Адрес сайта** в `https://bln.vladislavb.qzz.io` — этот адрес используется для QR-кодов, чеков и ссылок. Настройка применяется без перезапуска.

Адрес сайта также автоматически добавляется в разрешённые CORS origin. Если админка недоступна, аналогичные `PUBLIC_WEB_URL` и `CORS_ORIGINS` можно настроить в окружении API на VPS, сохраняя нужные старые origin. Проверьте, как именно запускается API: изменение переменных окружения может потребовать перезапуска, а прежний FTP-workflow при публикации API заново формирует `bln.env` из `SITE_DOMAIN`. Не заменяйте остальные настройки или секреты VPS.

В production cookie должны быть `Secure`; по умолчанию домен cookie не задан и они привязаны к хосту API. Если на VPS ранее вручную задавали `COOKIE_DOMAIN`, проверьте, что он не мешает работе `vps.vladislavb.qzz.io`. Не меняйте его без необходимости.

## 6. Проверка и откат

- Откройте `https://bln.vladislavb.qzz.io/`, а также `/bank/`, `/pos/`, `/services/` и `/admin/`.
- Проверьте вход и выход тестовым пользователем, сохранение сессии после обновления страницы, QR-ссылки и PWA. Не выполняйте реальные финансовые операции ради теста.
- В инструментах разработчика убедитесь, что запросы идут на VPS, ошибки CORS отсутствуют, а WebSocket `/ws` подключается и получает события. При ошибке проверьте разрешённый origin, HTTPS, cookie и поддержку WebSocket на пути к VPS.
- В случае ошибки в Pages можно откатиться к предыдущему развёртыванию через панель Cloudflare. При необходимости верните предыдущий адрес сайта в админке. База данных и DNS записи VPS не затрагиваются.

Для проверки CORS без входа можно выполнить (Linux/macOS):

```bash
curl -i -X OPTIONS 'https://vps.vladislavb.qzz.io/api/health' \
  -H 'Origin: https://bln.vladislavb.qzz.io' \
  -H 'Access-Control-Request-Method: GET'
```

После настройки в ответе должны присутствовать `Access-Control-Allow-Origin: https://bln.vladislavb.qzz.io` и `Access-Control-Allow-Credentials: true`. Это проверяет CORS, но не заменяет проверку входа и WebSocket в браузере.

Для локальной проверки сборки на Linux/macOS:

```bash
npm ci
BASE_PATH=/ VITE_API_URL=https://vps.vladislavb.qzz.io VITE_WS_URL=wss://vps.vladislavb.qzz.io/ws npm run build -w web
```

Файлы оказываются в `web/dist`; без этих переменных локальная сборка использует относительный `/api` для разработки, а не адрес VPS.

## Что происходит с прежним деплоем API

`.github/workflows/deploy.yml` сохраняет существующую сборку и FTP-публикацию API с его текущими секретами и настройками БД; фронтенд он больше не публикует. Автоматический запуск API в `main` теперь ограничен изменениями в `api/**` и `shared/**`; изменения только в `web/**` или workflow фронтенда API не перезапускают. При изменениях `shared/**` могут запуститься оба workflow. Если только корневой `package-lock.json` изменил зависимости API, обновление API запускается отдельно вручную после проверки.

Для справки, существующий API-workflow использует секреты окружения `production`:

| Секрет | Назначение |
| --- | --- |
| `FTP_API_HOST`, `FTP_API_USER`, `FTP_API_PASSWORD` | доступ для загрузки API |
| `FTP_API_DIR` | папка API, необязательно; по умолчанию `./` |
| `DB_NAME`, `DB_PASSWORD` | имя и пароль базы API |
| `DB_PORT`, `ADMIN_EMAILS` | необязательные порт БД и адреса администраторов |

В этом workflow по-прежнему заданы FTP-порт `2121`, `DB_HOST=db.vladinc.ru` и логин базы из `DB_NAME`; переменные `FTP_PROTOCOL` и `FTP_SECURITY` сохраняют прежнее назначение. Не меняйте эти настройки ради публикации фронтенда.

**Не запускайте `Deploy API` для публикации фронтенда:** он действительно загружает API и может его перезапустить. Новый workflow Pages не обращается к FTP, базе или настройкам VPS. Если позже потребуется ручной деплой API, проверьте выбранную ветку: в старых ветках может оставаться прежний workflow, который загружает и сайт, и API.
